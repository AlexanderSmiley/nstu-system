# NSTU System — система группы НГТУ (MVP: события-очереди)

Микросервисная система для организации работы учебной группы НГТУ. В MVP основной
сценарий — **событие-очередь**: преподаватель или староста создаёт событие (например,
сдачу лабораторной бригадами), участники встают в очередь по короткой ссылке, персонал
ведёт очередь и журнал сдач, а завершённые события архивируются.

## Роли

| Роль | Возможности в MVP |
|---|---|
| **ADMIN** | Ровно один администратор. Управление пользователями и названием сайта, все события, включая архив; восстановление и безвозвратное удаление архивных событий |
| **STAFF** | Создание и ведение событий, управление очередью, журнал, перенос хвоста, архивация закрытых событий |
| **STUDENT** | Вступление в очередь доступных событий `STUDENT+`/`GUEST+`, просмотр журнала (если он виден) |
| **GUEST** | Анонимная сессия по ссылке `/e/<slug>`: вступление в очередь `GUEST+` с указанием имени |

Очередь ведётся по статусам **ожидание** (`WAITING`), **пауза** (`PAUSED`),
**сдал** (`PASSED`). Сдавшие попадают в журнал; несдавшие переносятся в другое событие
(хвост). Закрытые события со временем автоматически архивируются.

## Архитектура

```
                браузер
                   │  http://localhost (80)
                   ▼
        ┌───────────────────────┐
        │ web (nginx)           │  SPA + проксирование /api
        └───────────┬───────────┘
                    │ /api/**
                    ▼
        ┌───────────────────────┐
        │ gateway :8080         │  единая точка входа, разбор JWT,
        └───────────┬───────────┘  /internal/** снаружи отдаёт 404
                    │
     ┌──────────────┼───────────────┬────────────────────┐
     ▼              ▼               ▼                    ▼
auth-service  student-service  event-service   notification-service
   :8081           :8082            :8083              :8084
     │              │               │                    │
     └──────────────┴───────┬───────┴────────────────────┘
                            ▼
          PostgreSQL (схемы auth / student / event)
          RabbitMQ (обменник nstu.events + DLQ)
```

Маршруты gateway: `/api/auth/**` → `auth-service`, `/api/students/**` →
`student-service`, `/api/events/**` → `event-service`, `/api/notifications/**` →
`notification-service`.

Сервисы compose (порт `web` публикуется только на loopback хоста):

| Сервис | Образ / сборка | Порт | Назначение |
|---|---|---|---|
| `web` | `web/Dockerfile` (nginx) | **127.0.0.1:${WEB_PORT} → 80 (host loopback)** | Раздача SPA и проксирование `/api` в gateway |
| `gateway` | `services/gateway/Dockerfile` | 8080 (внутренний) | Единая точка входа, маршрутизация, валидация access-токена |
| `auth-service` | `services/auth-service/Dockerfile` | 8081 (внутренний) | Аутентификация, пользователи, название сайта |
| `student-service` | `services/student-service/Dockerfile` | 8082 (внутренний) | Профили студентов |
| `event-service` | `services/event-service/Dockerfile` | 8083 (внутренний) | События, очередь, журнал, хвост, архивация |
| `notification-service` | `services/notification-service/Dockerfile` | 8084 (внутренний) | Подписка на доменные события (в MVP только логирует) |
| `db` | `postgres:16-alpine` | 5432 (внутренний) | Одна PostgreSQL, отдельная схема на сервис |
| `rabbitmq` | `rabbitmq:3.13-management-alpine` | 5672 / 15672 (внутренние) | Брокер сообщений (`nstu.events`, DLQ) |

Остальные порты доступны только внутри сети compose.

## Требования

- **Docker** и **Docker Compose** (плагин `docker compose`) — для запуска всего стека.
- **JDK 21** и **Node.js 22** — только для локальной сборки и запуска без Docker.

> **Важно (JDK 21 для локальной сборки backend).** Wrapper использует **Gradle 8.7**,
> который **не работает на JDK 25**. Перед локальной сборкой/запуском backend задайте
> JDK 21 в `JAVA_HOME`:
>
> ```bash
> export JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64
> ```
>
> (При сборке Docker-образов используется `eclipse-temurin:21-jdk-alpine`, поэтому
> локальный JDK для `docker compose` не нужен.)

## Требования к серверу

Стек рассчитан на небольшой VPS:

- **RAM: минимум 4 ГБ.** Суммарный лимит контейнеров — ≈ **3,3 ГБ**
  (`gateway` 384 + `auth-service` 448 + `student-service` 448 + `event-service` 640 +
  `notification-service` 320 + `db` 576 + `rabbitmq` 448 + `web` 64 МБ), плюс запас на
  ядро хоста и docker-демон. Меньше 4 ГБ почти гарантированно приведёт к OOM.
- **Диск: ~40 ГБ.** Полезные данные приложения малы — квота заметок **10 МБ на
  пользователя**, очередь/журнал/архив — текст. Место занимают в основном:
  - образы приложения и базовых сервисов (~1,5–2 ГБ);
  - кэш сборки BuildKit (1–3 ГБ; можно чистить `docker builder prune`);
  - ОС и чужие сервисы на том же хосте (в т.ч. Nginx Proxy Manager и его SSL/логи).

> **Сборка на сервере.** Компиляция образов (`Gradle` для пяти Java-сервисов и
> `npm` для frontend) запускает тяжёлые сборщики и **временно требует ещё +2–3 ГБ RAM**
> поверх лимитов рантайма. На VPS с 2 ГБ собирайте образы на другой машине и
> заливайте готовые, либо добавляйте swap и собирайте сервисы последовательно
> (`COMPOSE_PARALLEL_LIMIT=1`).

## Первый запуск

1. Создайте файл окружения и заполните секреты:

   ```bash
   cp .env.example .env
   ```

   Обязательно замените все значения `change-me`:
   - `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` — база и учётные данные PostgreSQL;
   - `RABBITMQ_DEFAULT_USER`, `RABBITMQ_DEFAULT_PASS` — учётные данные RabbitMQ;
   - `JWT_SECRET` — минимум **32 байта** случайных данных;
   - `INTERNAL_TOKEN` — токен внутренних вызовов между сервисами;
   - `ADMIN_USERNAME`, `ADMIN_PASSWORD` — учётные данные первого администратора.

   `SITE_NAME` задаёт название сайта по умолчанию и необязательно. Переменная
   `COOKIE_SECURE` читается `auth-service` и по умолчанию равна `false` (обычный HTTP);
   `COOKIE_SECURE=true` ставьте **только** при работе через HTTPS. Маршруты gateway
   (`NSTU_ROUTES_*`) имеют значения по умолчанию и в `.env` не нужны.

2. Соберите и запустите стек:

   ```bash
   docker compose up -d --build
   ```

3. Дождитесь статуса `healthy` у сервисов:

   ```bash
   docker compose ps
   ```

4. Откройте в браузере **http://localhost**.

## Первый вход администратора

- Войдите с логином `ADMIN_USERNAME` и паролем `ADMIN_PASSWORD` из `.env`.
- При первом входе система **обязательно** требует сменить пароль: новый пароль —
  **не менее 8 символов, содержит буквы и цифры**. Экран смены пароля нельзя обойти —
  до смены доступны только смена пароля, выход и чтение собственного профиля.

## Выдача аккаунта персоналу

1. Войдите как `ADMIN` и откройте **Администрирование → Пользователи**.
2. Создайте пользователя с ролью `STAFF` (персонал) или `STUDENT` (студент).
3. Сгенерированный временный пароль показывается **один раз** при создании — передайте
   его сотруднику. При первом входе сотрудник обязан сменить пароль.

Правила MVP: в системе ровно один `ADMIN`; роль `GUEST` через управление пользователями
не назначается (гостевая сессия создаётся по ссылке на событие).

## Событие и ссылка

Персонал или администратор создаёт событие со следующими полями:

- название (обязательно) и описание;
- доступность: `GUEST+` (по умолчанию), `STUDENT+`, `STAFF+`;
- дата/время начала (необязательно);
- лимит записей (по умолчанию **27**);
- единица записи: `BRIGADE` (по умолчанию) или `PERSON`;
- видимость журнала (по умолчанию — только персонал);
- срок хранения после завершения (по умолчанию **14 дней**).

Событие получает короткую ссылку **`/e/<slug>`**. Незалогиненный посетитель по ссылке
видит экран входа с кнопкой «Войти как гость»; войдя гостем, он указывает имя при
вступлении в очередь.

## Работа с очередью

Доступно персоналу и администратору на странице события:

- **«Далее»** — первая запись `WAITING` переходит в `PASSED` (сдал) и попадает в журнал;
- **пауза / возврат** — запись переводится в `PAUSED` и обратно с сохранением позиции;
- **перестановка** — изменение позиции активных записей;
- **удаление** — удаление активной записи;
- **перенос хвоста** — несдавшие переносятся в другое событие;
- **записи за участников** — добавление записи от имени персонала.

Студент и гость могут встать в очередь, выйти из неё самостоятельно и (для студента)
просматривать журнал, если он виден.

## Завершение и архив

- Персонал **закрывает приём** — событие переходит в `CLOSED`: очередь и журнал
  доступны только для просмотра, все изменения (вступление, «Далее», пауза,
  перестановка) отклоняются. Событие можно снова открыть.
- По истечении срока хранения закрытое событие **архивируется автоматически**
  (записи и журнал сжимаются, активная очередь очищается). Возможна и ручная архивация
  персоналом.
- Ссылка **`/e/<slug>` архивного события возвращает 404** всем, архив не показывается
  в активном списке. Персонал видит в истории только `CLOSED`, администратор — `CLOSED`
  и `ARCHIVED`.
- **Восстановление** (событие возвращается в `CLOSED`) и **безвозвратное удаление**
  доступны только `ADMIN`.

## Локальная разработка

### Backend

Задайте JDK 21 (см. «Требования»), затем собирайте и запускайте нужный сервис из
корня репозитория, например для `event-service`:

```bash
export JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64
services/event-service/gradlew -p services/event-service bootRun
```

Сборка и тесты сервиса:

```bash
export JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64
services/event-service/gradlew -p services/event-service build
services/event-service/gradlew -p services/event-service test
```

Тесты backend используют **Testcontainers**, поэтому для них нужен запущенный **Docker**
(поднимаются PostgreSQL и RabbitMQ).

### Frontend

В каталоге `web/`:

```bash
cd web
npm install
npm run dev     # dev-сервер Vite
npm run build   # сборка SPA
npm run test    # тесты (vitest)
npm run lint    # линтер (oxlint)
```

Dev-сервер Vite проксирует `/api` на **`http://localhost:8080`** (см.
`web/vite.config.ts`), поэтому для работы SPA нужен запущенный `gateway`. Проще всего
поднять инфраструктуру и backend через `docker compose up -d --build`.

## Обновление, перезапуск, остановка

```bash
docker compose up -d --build   # пересобрать образы и перезапустить изменённые сервисы
docker compose down            # остановить и удалить контейнеры (данные сохраняются)
docker compose down -v         # дополнительно удалить тома: данные PostgreSQL и RabbitMQ
```

> `docker compose down -v` **удаляет тома с БД и RabbitMQ** — используйте, только если
> готовы начать с чистого состояния.

## Безопасность и эксплуатация

- Все секреты храните только в `.env`; файл уже добавлен в `.gitignore` и не должен
  попадать в git. В репозиторий коммитится лишь `.env.example`.
- При работе через HTTPS/домен включите `COOKIE_SECURE=true` — cookie с токенами будут
  передаваться только по защищённому соединению.
- `/internal/**` недоступен снаружи: gateway отвечает на него `404`, внутренние вызовы
  защищены заголовком `X-Internal-Token`.
- Блокировка пользователя, сброс и смена пароля немедленно отзывают refresh-токены;
  уже выданный access-токен перестаёт действовать не позднее чем через **15 минут**.

## Что не реализовано в MVP

- **Telegram-бот** (`telegram-bot/`) и **alert-system** (`alert-system/`) — только
  README с контрактами, кода нет.
- **SMTP и восстановление пароля по email** — учётные записи создаёт администратор.
- **WebSocket/SSE** — очередь и журнал обновляются polling-запросами раз в ~5 секунд.
- **Мультигрупповость** — в схеме есть `group_id`, но используется одна группа.
- `notification-service` в MVP только логирует доменные события (уведомления не
  отправляются).

## Продакшн-развёртывание

Базовый `docker-compose.yml` публикует `web` только на **loopback**
(`127.0.0.1:${WEB_PORT}`), а override-файл `docker-compose.prod.yml` подключает `web` к
внешней docker-сети Nginx Proxy Manager (NPM) с сетевым алиасом `nstu-web`. Так NPM
достаёт контейнер напрямую по имени, без проброса порта на все интерфейсы хоста.
Все команды ниже выполняются из корня репозитория.

### 1. Клонирование и `.env`

```bash
git clone <repo-url> nstu-system
cd nstu-system
cp .env.example .env
```

Заполните `.env` по чеклисту:

- `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` — БД и учётные данные PostgreSQL;
- `RABBITMQ_DEFAULT_USER`, `RABBITMQ_DEFAULT_PASS` — учётные данные RabbitMQ;
- `JWT_SECRET` — **минимум 32 байта** случайных данных (HS256);
- `INTERNAL_TOKEN` — токен внутренних вызовов между сервисами;
- `ADMIN_USERNAME`, `ADMIN_PASSWORD` — учётные данные первого администратора;
- `WEB_PORT=8080` — порт `web` на loopback-интерфейсе хоста (наружу не публикуется);
- `NPM_NETWORK=remnawave-network` — имя внешней docker-сети NPM
  (узнать на сервере: `docker network ls`);
- `COOKIE_SECURE=true` — **при работе за HTTPS** (см. шаг 4);
- `NSTU_CORS_ALLOWED_ORIGINS=https://<домен>` — публичный origin, иначе браузерные
  POST-запросы будут отбиваться 403 (same-origin проверка gateway).

### 2. Сборка и запуск

На VPS со скромной RAM собирайте образы **последовательно**, чтобы `Gradle`/`npm`
не съели память одновременно (на время сборки нужно +2–3 ГБ RAM, см. «Требования к серверу»):

```bash
COMPOSE_PARALLEL_LIMIT=1 docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
```

Проверьте, что все 8 сервисов поднялись и стали healthy:

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml ps
```

### 3. Proxy Host в Nginx Proxy Manager

В NPM создайте **Proxy Host**:

- **Domain Names** — ваш домен;
- **Scheme** — `http`;
- **Forward Hostname** — `nstu-web` (сетевой алиас контейнера `web` из `docker-compose.prod.yml`);
- **Forward Port** — `80`.

TLS терминирует NPM: до контейнера трафик идёт по HTTP внутри docker-сети, а приложение
узнаёт про HTTPS из заголовка `X-Forwarded-Proto` (gateway настроен на
`forward-headers-strategy: framework` и использует схему из этого заголовка для
same-origin проверок).

### 4. TLS

1. Сначала попробуйте встроенный в NPM Let's Encrypt: в Proxy Host → **SSL** →
   **Request a new SSL Certificate**, включите **Force SSL**.
2. Если встроенный ACME не сработает (нет доступа к Let's Encrypt или занят 80-й порт),
   запасной путь — ручной `certbot` с DNS-задачей:

   ```bash
   certbot certonly --manual --preferred-challenges dns -d <домен>
   ```

   Подтвердите владение доменом, создав TXT-запись `_acme-challenge.<домен>` с выданным
   значением (продление — вручную раз в ~90 дней). Затем в NPM Proxy Host → **SSL** →
   **Custom Certificate** вставьте содержимое
   `/etc/letsencrypt/live/<домен>/fullchain.pem` и
   `/etc/letsencrypt/live/<домен>/privkey.pem`.
3. После включения HTTPS выставьте в `.env`:

   ```
   COOKIE_SECURE=true
   NSTU_CORS_ALLOWED_ORIGINS=https://<домен>
   ```

   и перезапустите `auth-service` (cookie-флаг и CORS перечитываются при старте):

   ```bash
   docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d auth-service
   ```

### 5. Проверка

`docker compose ... ps` должен показать 8/8 healthy; откройте `https://<домен>` — появится
экран входа. Порты `db`, `rabbitmq` и backend-сервисов наружу не публикуются вовсе, а
`web` слушает только `127.0.0.1:${WEB_PORT}`.
